## 二、高优先级问题（建议立即处理）

### 1. 两个潜伏的运行时崩溃（ruff 已报，未修复）

- `finfeed/storage/database.py:1241` —— `NewsDatabaseManager._row_to_news(row)`，但该类实际名为 `NewsDatabase`（第 29 行定义）。`db_news_without_content()` 一旦执行到该行必然抛 `NameError`。这是类重命名后的漏改，属于"定时炸弹"。
- `finfeed/llm/analyzer.py:422-423` —— 内部函数 `_map_digests()` 里 `prompt_tokens += ...`，但外层计数器 `prompt_tokens`（第 336 行）在该函数内未声明 `nonlocal`（对比第 349、371 行的其他函数都声明了）。多批次压缩路径一触发就是 `UnboundLocalError`。

**建议**：修复这两处，并为 `db_news_without_content` 和多批次 LLM 路径补回归测试。

### 2. ruff 门禁形同虚设

配置里明确写着"提交前拦截"，但当前主分支就有 20 个未修复错误（13 个可自动修复）：

- 4 处未使用导入、4 处未使用变量、2 处空 f-string、3 处 import 排序、1 处缺文件末尾换行，均可 `python -m ruff check . --fix` 一键处理。
- 仓库没有任何 CI 配置（无 `.github/`），门禁完全依赖自觉，已经失效。

**建议**：先跑 `ruff check --fix` 清掉存量；随后接入 CI（哪怕只是 ruff + pytest 两个步骤），让门禁真正生效。

### 3. 测试覆盖严重不足

- 20 个测试文件对应 19 个源码模块，覆盖的主要是 parser、alerts、llm 等边缘模块。
- 最大的核心模块 `market/store.py`（1827 行）、`storage/database.py`（1373 行）、`screener/`（20 个文件）几乎无测试。
- 测试运行伴随大量告警（test_ml_engine.py 单文件 200 条 `ConstantInputWarning`），提示测试数据构造可能不严谨。

**建议**：优先为 `database.py` 的 CRUD 和 `store.py` 的建表/迁移逻辑补测试——这两处是数据地基，回归代价最高。

## 三、架构与结构问题（建议中期重构）

### 4. 上帝模块集中爆发

| 文件 | 行数 | 问题 |
|---|---|---|
| `market/store.py` | 1827 | 0 个类、59 个顶层函数，十余张表的 DDL + CRUD 全部堆在一个文件 |
| `storage/database.py` | 1373 | `NewsDatabase` 类 36 个方法，另有 35 个顶层镜像函数，双重 API 表面 |
| `market/ths_limitup.py` | 1267 | 数据清洗、多源抓取、合并逻辑混在一起 |
| `cli.py` | 869 | 混合 Web 启停、日志配置、进程管理、子命令分发四种职责 |

**建议**：按"表域"拆分 `store.py`（如 `store/limit_pool.py`、`store/money_flow.py`）；`database.py` 的顶层镜像函数只保留一层，逐步让调用方直接用类。

### 5. 双轨实现并存

- `finfeed/content_extractor.py` + `content_fetch.py`（包根目录，30KB 级）与 `core/parsers/` 形成两套解析体系，`content_fetch.py` 中大量 `# noqa: BLE001` 标注的宽泛捕获暗示这是早期遗留副本。
- `analysis/universe.py` 与 `market/universe.py` 都在做 stock_meta 填充，入口语义重叠。
- `ui/web/`（旧）与 `ui/web_fastapi/`（新）双轨，pyproject 注释也承认是"方案 D 双轨并行"——需要给出旧版下线时间表。

### 6. 分层被反向依赖穿透

- `llm/__init__.py` 反向导入 `application` 层；`sector_minute/collector.py:21` 直接导入 `capital_dashboard.tdx.ensure_alive`。
- 函数内延迟 import 至少 30 处（`cli.py`、`alerts/subscription.py` 等），多数是循环依赖的补丁。

**建议**：确立 `core → application → ui` 单向依赖规则，用 ruff 的 import-linter 思路或简单的 CI grep 检查拦截反向导入。

### 7. 并发安全隐患

- 单例无锁保护：`core/dedup.py:70`、`core/parsers/forum_parsers/base.py:65` 用 `__new__` 实现单例。
- 模块级可变缓存无并发保护：`ui/web/shared.py:87 _api_cache`、`f10/ths_config.py:84 _soup_cache`。
- `global` 可变标志：`alerts/store.py:74`、`analysis/crossref.py:124`、`cli.py:628`。

Web 端（FastAPI）是多线程/异步环境，这些缓存与标志存在竞态窗口。建议缓存统一加锁或换用 `functools.lru_cache`/TTLCache。

## 四、代码规范问题

### 8. 错误处理反模式

- `except Exception` 大量分布，`content_extractor.py:319/348/379/390`、`content_fetch.py:165/177/184/396` 均带 `noqa` 标记——已知但长期未治理。
- 静默吞异常：`utils/time_utils.py:39-40` 捕获 `ValueError/TypeError` 后直接 `pass`，时间解析失败无任何信号。
- 对"整源静默丢失"类问题，项目历史上已经踩过坑（见 commit `0baa025`：法布财经哨兵碰撞），但吞异常的习惯仍在。

### 9. 日志与调试输出

- `finfeed/` 下共 50 处 `print(`，非 CLI 残留集中在 `f10/http_client.py`（6 处彩色终端输出）和 `f10/utils/logger.py:28`（stderr print），库代码不应直接打印。
- 项目同时配置了 black、isort、ruff format 三套格式工具，且 black 与 ruff format 的行长/引号规则重叠，建议只保留 ruff（check + format），移除 black/isort 减少配置漂移。

### 10. 类型注解新旧混用

`requires-python = ">=3.10"` 但大量代码仍用 `List[...]`、`Optional[...]`（ruff 的 UP 规则因此被刻意排除）。建议在独立"现代化专项"中分批迁移到 `list`、`X | None`，迁移后即可把 UP 纳入门禁。

## 五、依赖与安全

### 11. 依赖锁定隐患

`pyproject.toml` 中 `pydantic-core = "==2.46.4"` 硬钉补丁版本，注释说明是为规避版本不匹配。这会把包钉死在单一补丁版本上，后续升级 pydantic 时容易连锁失败。建议改为与 pydantic 官方匹配表对齐的区间约束，并考虑提供完整的锁文件（`pip-compile` 或 `uv lock`）保证可复现安装。

### 12. 安全点

- `f10/api/eastmoney.py:15` 硬编码了第三方接口 token，建议移入配置并确认是否需轮换。
- 15 处 f-string 拼接 SQL（`database.py:179/617/986`、`market/store.py:424/426` 等）。已核对均为内部白名单表名/列名拼接、值走参数化，无注入风险，但建议收敛为一个 `_quote_ident()` 辅助函数，杜绝未来引入用户输入。
- `.gitignore` 已覆盖 `logs/` 与 `*.db`，但 `finfeed/logs/screener_tasks.db`（1.3MB）已存在于源码包内——运行时数据不应落在包目录，建议迁移到用户数据目录（如 `platformdirs` 提供的路径）。
